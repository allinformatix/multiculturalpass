# Erstinstallation

1. Nach Freigabe „Use this template“ verwenden beziehungsweise dieses lokale Verzeichnis als eigenes Repository veröffentlichen und in GitHub als Template markieren. Bis dahin lokal arbeiten. Python 3.12+, Bash 3.2+, Terraform 1.13.5, Ansible gemäß requirements.txt, OpenSSH, curl, GitHub CLI und Docker Compose installieren. Für Prüfungen zusätzlich ShellCheck und die Python-Lintpakete. Linux/macOS sind Controller; der Zielhost ist Ubuntu 24.04 amd64.
2. `cp config/project.example.json config/project.json`; Slug global eindeutig wählen, HCP-Organisation, GitHub-Repository, SSH-Public-Key und ACME-Mail angeben. In jedem Environment echte Domain, Zone-ID und feste Administrator-/Runner-Egress-CIDRs hinterlegen. Keine Beispieldomains oder Dokumentations-CIDRs für echte Infrastruktur verwenden.
3. Bestehende Cloudflare-Zone voraussetzen. SSL auf Full (strict) setzen. Cache-Regeln wie in [cloudflare.md](cloudflare.md) einrichten. Tokens wie in [security.md](security.md) bereitstellen; keine vorhandenen APOII-Secrets kopieren. DB-/Odoo-Passwörter als 32–128 Hexzeichen erzeugen, etwa mit `openssl rand -hex 32`; alle vier Werte getrennt erzeugen. Für RESTIC_PASSWORD einen separaten langen Zufallswert außerhalb des Hosts sichern.
4. Credentials in der lokalen Prozessumgebung oder in GitHub Environment Secrets hinterlegen. Das Template lädt keine `.env` per `source`. GH_TOKEN/gh-Login nur für Initialisierung und CI-Gates erforderlich. AWS-Zugänge müssen das Erstellen des S3-Buckets erlauben; für späteren Hostbetrieb separat auf den Bucket begrenzen.
5. `./ops.sh doctor --env dev` prüft lokale Werkzeuge, Konfiguration und lesende Provider-Authentifizierung. `./ops.sh init --env dev` erstellt HCP-Projekt/Workspace und ein GitHub-Environment, dann initialisiert es Terraform. Für stg/prd wiederholen. Bestehende Schutzregeln werden erhalten. Bei prd zuerst Reviewer in GitHub konfigurieren und init erneut ausführen.
6. `./ops.sh plan --env dev` ausführen und `.runtime/dev/plan.txt` prüfen. `./ops.sh provision --env dev --confirm customer-odoo-dev:apply` erstellt kostenpflichtige Infrastruktur. Name an den gewählten Slug anpassen. Mit `apply` kann der bereits geprüfte Plan verwendet werden; Änderungen an Konfiguration/Terraform nach Plan werden erkannt.
7. Den SSH-Hostfingerprint über die authentifizierte Hetzner-Konsole (`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`) prüfen. Den dazugehörigen öffentlichen Hostschlüssel mit der VM-IP in `~/.ssh/known_hosts` hinterlegen. `ssh-keyscan` allein ist kein Vertrauensnachweis. Eigenen privaten SSH-Key sicher laden. Für einen frischen Host `BOOTSTRAP_SSH_USER=root ./ops.sh configure --env dev` verwenden. Ansible prüft den neuen Deployment-Zugang vor Abschaltung von Root-SSH. Danach BOOTSTRAP_SSH_USER entfernen beziehungsweise in CI auf deploy setzen.
8. NGINX erhält ein öffentlich vertrauenswürdiges DNS-01-Zertifikat. `./ops.sh status --env dev` prüft SSH/Compose und HTTPS `/web/health`. Anmeldung an der konfigurierten Domain mit `admin` und ODOO_ADMIN_PASSWORD testen, Passwort/Benutzerzugriff nach Richtlinie verwalten. Die Datenbank wird ohne Demo-Daten initialisiert; der Datenbankmanager ist gesperrt.
9. `./ops.sh backup-init --env dev --confirm customer-odoo-dev:init-backup` einmalig ausführen, dann `./ops.sh backup --env dev`. Ein vorhandenes Restic-Repository wird niemals wegen eines fehlgeschlagenen Authentifizierungschecks neu initialisiert. Timerstatus und Snapshots prüfen, Restore-Drill durchführen.
10. Cloudflare DNS/TLS/WebSockets, SMTP, geschlossene Ports und einen Addon-/Attachment-Test gemäß [DR-Abnahme](disaster-recovery.md) prüfen. Erst nach dieser Abnahme produktive Daten übernehmen.

Erst-Provisionierung und Hostschlüsselverifikation sind notwendige Bootstrap-Schritte. Auf bestehenden verifizierten Hosts führt `./ops.sh deploy --env dev` die vollständige Kette aus; in nichtinteraktiver Ausführung `--confirm SLUG-dev:apply` angeben.
